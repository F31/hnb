# API Compatibility Review: adopt-nats-jetstream-messaging

## Scope

Verify that the NATS JetStream adoption introduces no breaking changes to external-facing APIs.

## Public HTTP API

| Endpoint | Change | Breaking? |
|----------|--------|-----------|
| `POST /operations` | Accepts new fields via EventEnvelope extension (operationId, stepId, expectedVersion, resourceId as optional) | No — new optional fields only |
| `GET /operations/{id}` | No change | No |
| `GET /operations/{id}/events` | No change | No |
| `GET /operations/{id}/progress` | No change | No |
| `POST /providers/{id}/actions` | No change | No |

**Conclusion:** All public HTTP API endpoints remain wire-compatible. The EventEnvelope additions are optional and backward-compatible per JSON Schema `additionalProperties: false` + `oneOf` constraints.

## Provider API

Provider contracts are unaffected. The change only affects how Operation Steps are dispatched internally (PostgreSQL polling → JetStream durable consumer). Provider APIs continue to receive:

- Same request payloads
- Same idempotency keys
- Same expected version headers
- Same response format

**Conclusion:** No breaking changes to Provider SPI.

## RuntimeTarget API

RuntimeTarget API is not involved in this change. Operation execution continues through the same Provider API path.

**Conclusion:** N/A — no change.

## Database Migration

| Schema | Change | Scope |
|--------|--------|-------|
| `outbox_events` | Extended with operation_id, step_id, expected_version, resource_id columns | Internal — no public API exposure |
| `worker_leases` | New table for fencing tokens | Internal |
| `consumer_checkpoints` | New table for replay tracking | Internal |
| `operation_steps` | Extended with checkpoint, fencing_token columns | Internal |

All migrations are additive (new columns, new tables) and internal to the Operation Store. No public API schema or Provider schema is modified.
