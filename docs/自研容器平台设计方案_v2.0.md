# 自研容器平台 2.0 设计方案
## Kamaji + CAPI 统一多模式集群管理平台

版本：v2.0 | 日期：2026-10-15 | 状态：评审稿

---

# 1. 设计目标与原则

**目标**：以最小化 Kubernetes 1.37 发行版为底座，构建同时支持 HCP（Hosted Control Plane）、传统 CAPI 集群、独立集群纳管三种模式的企业级容器平台，并通过七个差异化能力形成对 Rancher/OpenShift/云厂商产品 的竞争优势。

**核心原则**：

1. **单一声明式入口**：所有集群生命周期操作（创建/升级/伸缩/删除）通过管理集群中的 CAPI CRD + GitOps 完成，不依赖自研 REST API。
2. **管理集群只编排、不承载业务**：租户工作负载永不调度到管理集群（HCP 控制面 Pod 除外，且运行于专用节点池）。
3. **分发版中立**：平台自身与产物集群均为原生 K8s，不绑定任何商业发行版。
4. **数据面统一**：成本、健康度、合规状态等管理数据跨三种集群模式汇聚到同一数据面，这是全部差异化能力的根基。
5. **Alpha 特性开关化**：所有依赖 K8s Alpha API 的能力做成可开关的实验特性，默认关闭。

# 3. 管理集群设计

| 项 | 决策 |
|---|---|
| 发行版 | k0s（轻量、单一二进制、与 Kamaji/CAPI 组合兼容良好），3 控制面节点 HA |
| CAPI | 核心 Cluster/Machine API，Contract v1beta2 |
| HCP | Kamaji operator + Kamaji CAPI Control Plane Provider（单一 Provider 策略） |
| 数据存储 | CloudNativePG 管理的 PostgreSQL（Kamaji kine 后端），HA 3 实例 + PITR |
| CNI | Cilium（Hubble 可观测、NetworkPolicy、ipvs 已废弃背景下的首选） |
| GitOps | Flux CD（direct reconcile CAPI CRD） |
| 证书 | cert-manager（Kamaji 客户端证书、租户 API Server 入口证书统一签发） |

**加固要求（平台级 SLO 的根基）**：
- 控制面组件运行于专用节点池，与工作负载/HCP Pod 物理隔离；
- 每个租户命名空间：ResourceQuota + LimitRange + PodDisruptionBudget + PriorityClass（租户控制面 Pod 高于平台组件、低于系统组件）；
- 管理集群 etcd 每日备份 + 季度恢复演练，RPO≤1h、RTO≤2h；
- PostgreSQL 数据存储：cert 客户端认证、每租户独立 database/schema、独立备份策略。

# 4. 统一资源模型与三种集群模式

**ClusterClass + clusterctl 模板** 作为集群创建的标准机制（提前至阶段一建设）。

| 模式 | 表达方式 | 生命周期 |
|---|---|---|
| HCP 托管 | `Cluster` + `KamajiControlPlane` + `MachineDeployment` | CAPI 全编排 |
| 传统 CAPI | `Cluster` + `KubeadmControlPlane` + `MachineDeployment` | CAPI 全编排 |
| 独立纳管 | 自研 `ClusterInventory` CRD + kubeconfig Secret | 只读监控 + kubeconfig 分发，不承诺升级/伸缩 |

**Bootstrap 策略（阶段零 PoC 定论）**：
- 首选：kubeadm 引导流程——与 Kamaji CAPI Provider 原生契合（证书/kubelet-config 按 kubeadm 约定生成）；
- 备选：Talos——需解决 CA 注入（使用 Kamaji 生成的 TCP 级 CA，禁用 KubePrism、kubelet 直连控制面）、kubelet 版本对齐（与控制面 minor 差 ≤3）、CNI 首装 chicken-and-egg（首装直连 API Endpoint）。

**基础设施 Provider**：CAPV（vSphere）/CAPO（OpenStack）/Metal3（裸金属）；工作节点 OS 与引导方式解耦选型。

**纳管边界**：独立集群仅纳入统一监控/告警/审计视图与 kubeconfig 托管，控制台明确标注"非生命周期管理"，避免对不可控集群承诺升级。

# 5. HCP 数据面设计（PostgreSQL）

- **架构**：`kamaji-etcd.deploy=false`；CloudNativePG 提供 HA PostgreSQL；DataStore CR `driver: PostgreSQL`；operator 级默认 + TCP 级 `spec.dataStore` 覆盖，支持分池。
- **隔离模型**：普通租户共享 PG 实例（kine 表级隔离 + 独立 database）；大客户/高写租户独立 DataStore 或独立 PG 实例。
- **认证**：cert-manager 签发客户端证书（Kamaji tlsConfig 预期证书认证；云厂商托管 PG 不支持客户端证书的场景不可用）。
- **运维**：关注 kine 表膨胀与定期 vacuum；pg_dump/basebackup + PITR 备份；与 etcd 路径做写 QPS 基准对比后确定租户分池策略。
- **升级策略（最高危变更）**：kine/PG 升级影响所有共享租户——独立升级窗口、按租户分批、升级前强制快照、自动回滚预案。不允许与应用发布窗口合并。

# 6. 网络设计

| 层 | 决策 |
|---|---|
| 控制面→工作节点 | Konnectivity 反向隧道（HCP 模式强制） |
| 租户 API 入口 | Gateway API / Envoy TLS passthrough（SNI 路由）；起步用共享入口 + 每租户 SNI 域名，关键租户可升级 per-tenant 代理；cert-manager + DNS 自动化签发 |
| CIDR 管理 | CAPI in-cluster IPAM provider，Pod/Service CIDR 声明式分配，杜绝多集群冲突 |
| 东西向 | Cilium ClusterMesh（跨集群）+ NetworkPolicy（租户隔离） |
| 废弃项 | kube-proxy ipvs 模式（1.37 已废弃）→ nftables/Cilium 原生路径 |

# 7. 多租户与配额

- **管理集群层**：每租户独立命名空间运行其 HCP 控制面 Pod；RBAC 绑定租户身份，仅能操作自有命名空间；
- **配额三层模型**：单集群 ResourceQuota → 跨集群联邦配额（自研 Budget Controller）→ 租户预算（货币维度）；
- **策略即代码**：Kyverno 集群策略（镜像来源、资源限制、网络策略基线），策略例外走审批工作流。

# 8. 差异化能力（七大特性）

## 8.1 无重启资源自治 ★核心壁垒
- 基座：In-Place Pod Resize（1.35 GA）+ VPA `InPlaceOrRecreate` 模式；1.37 调度器 resize 抢占为 Alpha → **实验开关**；
- 闭环：用量采集（metrics.k8s.io 已 GA）→ right-sizing 建议（控制台人工确认起步）→ 原地调整 requests/limits，零重启；
- 增强：结合 8.4 预算约束，超预算租户的建议优先降配而非扩容。

## 8.2 环境自动休眠与唤醒 ★快速见效
- 基座：HPA scale-to-zero（1.37 Beta 默认开启）；
- 能力：dev/test/预览环境闲置 N 小时自动 scale-to-zero → 请求触达或定时自动唤醒；HCP 集群可进一步休眠控制面 Pod（PG 存储无需快照即可重启）；
- 产出：每租户闲置成本报告，目标回收 30%+ 闲置算力。

## 8.3 AI 算力治理 ★战略投入
- 基座：DRA（1.37 device taints Stable + 扩展资源 GA）；CompositePodGroup（Alpha）→ 实验开关；
- 能力：GPU 池化与按团队配额、故障卡自动驱逐替换（device taint）、训练任务 gang scheduling、推理服务 scale-to-zero、按卡时/任务计费（对接 8.4 成本数据面）。

## 8.4 预算感知准入 ★CFO 视角
- 自研 Budget Controller：租户预算配额（跨集群联邦）→ 超预算时新负载排队/降配/自动转 spot，而非直接失败；
- 数据源：OpenCost 采集 → 归一化到租户-集群-命名空间三级 → 平台数据面统一存储。

## 8.5 平台金丝雀升级
- 集群版本灰度：canary 集群先行 → 健康度指标（API 延迟、错误率、工作负载就绪率）达标 → 自动批次推进 → 异常自动暂停；
- 适用于：K8s 小版本升级、节点 OS 升级（不可变 OS 原地替换）、Kamaji operator 升级。

## 8.6 零信任工作负载身份
- 基座：Pod Certificates + Cluster Trust Bundles（1.37 Stable）；
- 能力：免 sidecar 的短周期自动轮转 mTLS（工作负载间 + 工作负载到数据服务），面向等保合规客户。

## 8.7 审计证据自动化
- 持续 CIS Benchmark 扫描 + 配置漂移检测 + 证据包自动生成（等保/SOC2 模板）；
- 纳入 Fleet Controller 数据面，覆盖三种集群模式。

# 10. 风险清单（Top）

| 风险 | 缓解 |
|---|---|
| Kamaji 无 stable 版本线 | digest 锁定 + 内网镜像 + 金丝雀升级 + 备份回滚预案 |
| 数据存储（PG）升级爆炸半径 | 最高危变更独立编排，租户分批，强制快照 |
| Talos bootstrap 兼容性 | 阶段零 PoC 定论；默认 kubeadm 流程 |
| 共享 API 入口单点 | 关键租户 per-tenant 代理选项；入口层多副本跨节点 |
| Alpha 特性回退 | 全部实验开关化，默认关闭，升级前兼容性检查 |

# 11. 落地路径

| 阶段 | 周期 | 交付物 |
|---|---|---|
| **阶段零：引导链路 PoC** | 2-4 周 | Kamaji + CAPI provider + bootstrap（kubeadm/Talos 二选一定论）+ Konnectivity + CNI 首装全链路打通；CA、版本 skew、首装问题全暴露 |
| **阶段一：CAPI 基础** | 1-2 月 | 管理集群（k0s 3 节点 + PG + 加固）、传统 CAPI 集群声明式管理、ClusterClass 模板、GitOps 流水线 |
| **阶段二：HCP + 数据面** | 2-3 月 | Kamaji HCP 集群上线、PG DataStore 分池、租户 RBAC/隔离、FinOps 数据面（OpenCost）、**8.2 环境休眠首发** |
| **阶段三：差异化深化** | 持续 | 8.1 资源自治 → 8.4 预算准入 → 8.5 金丝雀升级 → 8.6/8.7 合规线 → 8.3 AI 算力（视公司战略） |
| 贯穿 | — | Web 控制台统一展示三模式集群；审计证据自动化 |

# 12. 关键技术决策汇总

| 决策点 | 结论 |
|---|---|
| HCP Provider | Kamaji 单选；edge release 自建治理 |
| 数据存储 | CloudNativePG（PostgreSQL），cert 认证，分池隔离 |
| 引导 | kubeadm 流程默认；Talos 为阶段零结论项 |
| 节点 OS | Talos（安全优先）或 k0s（简单优先），与引导解耦 |
| CNI | Cilium（废弃 ipvs） |
| 集群模板 | ClusterClass + clusterctl |
| API 入口 | Gateway/Envoy SNI + cert-manager |
| IPAM | CAPI in-cluster IPAM |
| GitOps | Flux CD |
| 纳管 | 自研 Fleet/Inventory Controller，只读边界 |
