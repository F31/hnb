# 1. 文档目的

本文档定义一套面向企业生产环境的云原生平台需求和技术架构。平台以Kubernetes为核心资源编排底座，通过统一控制面管理多租户、多个异构集群和多地域资源，以插件方式提供容器网络、容器存储、GPU、数据库、中间件、微服务、容器安全、统一容灾和可观测运维能力。

平台建设不追求将所有云原生项目简单集成到一个控制台，而是建立一个：

- **可靠的平台**：控制面高可用，数据面自治，故障不扩散，操作可恢复；
- **开放的平台**：遵循Kubernetes、CNI、CSI、OCI、OpenTelemetry等标准；
- **可扩展的平台**：微内核、插件化、Provider化，底层实现可以替换；
- **安全的平台**：租户隔离、统一身份、最小权限、镜像安全、运行时安全和审计闭环；
- **轻量的平台**：核心依赖少，功能按需安装，避免强制部署重型组件；
- **高性能的平台**：快慢路径分离，增量同步，数据本地处理，热点模块可使用Rust；
- **简单易用的平台**：以租户、项目、环境、应用和服务为中心，屏蔽底层复杂性；
- **可持续运行的平台**：支持单节点到高可用、单中心到双活灾备的渐进式演进。

# 2. 输入材料评审与优化原则

## 2.1 对参考白皮书的吸收

参考白皮书中以下能力具有较高借鉴价值：

1. 统一管理多个Kubernetes集群和异构基础设施；

3. 支持Cilium、Calico、Kube-OVN等多种容器网络；
4. 支持外部存储、Rook-Ceph分布式存储和TopoLVM本地存储；
5. 通过Operator简化数据库、中间件和有状态服务管理；
6. 提供联邦集群、跨集群应用和灾备能力；
7. 支持整卡GPU和vGPU资源配置；
8. 提供监控、日志、事件、审计、巡检和告警；
9. 通过OperatorHub和应用目录降低扩展能力使用门槛。

## 2.2 不直接照搬的内容

以下设计不直接进入本期核心：

- DevOps工具链和持续集成；
- 强绑定Jenkins、Tekton、GitLab等工具；
- 默认强制安装Service Mesh；
- 将所有数据库、中间件和存储组件编译进核心；
- 将理论规模或其他产品测试结果直接作为本平台承诺；
- 将Karmada、HAMi、Cilium或Rook-Ceph设置为不可替换的内核依赖；
- 将所有Kubernetes原生对象直接暴露给普通用户。

## 2.3 核心优化原则

### 2.3.1 先建立核心闭环，再扩展生态

核心闭环包括：

```text

→ 项目与环境
→ 应用运行
→ 网络与存储
→ 监控与告警
→ 安全与审计
→ 数据库和中间件服务
```

联邦、多网络、GPU虚拟化、分布式存储和Service Mesh均以插件方式按需启用。

### 2.3.2 产品需求与具体实现分层

产品层定义稳定能力，例如：

- 集群；
- 网络配置；
- 存储配置；
- 加速器资源池；
- 联邦调度策略；
- 数据库实例；
- 中间件实例。

实现层可以使用Cilium、Kube-OVN、HAMi、Karmada或其他兼容组件，上层API和用户体验不因实现替换而变化。

# 3. 产品定位

## 3.1 产品定义

> **HNB Cloud是一套面向多租户企业应用、容器、数据服务和中间件统一运营的云原生平台，通过微内核控制面、插件化能力中心、分布式集群Agent和统一灾备管理，实现多集群、多基础设施、多组织和多服务类型的统一管理。**

平台不是单纯的Kubernetes Dashboard，也不是多个开源控制台的入口集合。

平台使用两个相互独立但可以关联的管理维度：

- **组织部门**：描述集团、公司、事业部、部门和人员的管理关系；
- **租户**：描述资源、安全、配额、审计、成本和服务使用边界。

组织部门与租户通过`TenantOrgBinding`建立多对多关联：

```text
企业组织目录                     云资源租户
集团                            Tenant A
├── 事业部一 ────────────────┐  ├── Project A1
├── 事业部二 ────────┐       ├─ Tenant B
└── 共享中心 ────────┴───────┘  └── Project B1
```

规则如下：

1. 一个租户可以关联多个组织部门；
2. 一个组织部门可以参与多个租户；
3. 一个项目只能归属一个租户；
4. 跨租户资源共享必须通过受控的共享对象、授权和审计完成；
5. 租户删除前必须完成项目、资源、账单、审计和数据的处置。

普通用户主要管理：

```text
租户
└── 项目
    └── 环境
        ├── 应用
        ├── 数据库服务
        ├── 中间件服务
        ├── 网络、存储和GPU配额
        └── 灾备保护策略
```

平台自动处理：

- Kubernetes资源生成；
- 租户和项目隔离；
- 网络和存储绑定；
- GPU调度；
- 账号和凭据；
- 镜像与运行时安全；
- 监控、日志和链路；
- 备份、恢复和容灾切换；
- 跨集群传播与故障转移；
- 资源申请和审批状态。

# 5. 总体设计原则

## 5.1 微内核

平台核心只承担不可缺少的公共能力：

1. 统一API和身份上下文；
2. 组织目录、租户、项目和环境；
3. 统一资源模型；
4. Operation异步操作引擎；
5. 插件注册和生命周期；
6. 权限、策略和审计；
7. 集群Agent连接和任务分发；
8. 事件总线；
9. 状态快照和资源关系图谱；
10. 配置、密钥引用和能力发现；
11. 租户与组织映射；
12. ResourceRequest与轻量审批扩展点；
13. 灾备保护组、策略、计划和执行记录。

以下能力不得直接编译进核心：

- CNI；
- CSI；
- Karmada；
- HAMi；
- 数据库Operator；
- 中间件Operator；
- Service Mesh；
- 可观测存储；
- 云厂商API适配。

## 5.2 控制面与数据面分离

- 中心控制面负责配置、编排、治理和状态聚合；
- 工作集群负责应用、数据库、中间件、网络、存储和GPU实际运行；
- 控制面故障时，已运行数据面继续工作；
- 集群Agent断连时，Kubernetes和Operator继续本地调和；
- 控制面恢复后通过增量同步和周期校准恢复状态；
- 业务流量、数据库流量和消息流量不经过平台控制面。

## 5.3 普通多集群与联邦集群分离

### 普通多集群纳管

用于：

- 统一资产；
- 权限和项目管理；
- 监控与运维；
- 独立集群部署；
- 数据服务管理。

每个集群保持独立，不要求安装Karmada。

### Karmada联邦

用于：

- 同一应用跨集群部署；
- 跨地域副本分布；
- 集群故障迁移；
- 多云和混合云调度；
- 统一传播和差异化配置。

联邦能力是可选插件，不能成为单集群用户的部署前置条件。

## 5.4 声明式、幂等和最终一致

- 所有资源以期望状态描述；
- Controller持续调和期望状态和实际状态；
- 创建、升级、扩容、备份和恢复支持幂等；
- 所有长任务持久化状态；
- 操作失败后可重试、恢复、取消或补偿；
- API重复提交不得产生重复资源；
- 状态允许最终一致，权限和审计必须强一致。

## 5.5 快慢路径分离

### 快路径

- 资源列表；
- 当前状态；
- 应用拓扑；
- 告警和事件；
- 权限校验；
- 资源查询。

快路径只读取中心Read Model、缓存和查询存储，不实时遍历远端集群。

### 慢路径

- 集群创建；
- 插件安装；
- 网络和存储变更；
- 应用发布；
- 数据库和中间件创建；
- GPU驱动部署；
- Karmada传播；
- 备份恢复。

慢路径通过Operation异步执行，并使用SSE或WebSocket推送进度。

## 5.6 默认安全与渐进增强

- 默认启用基础网络隔离和Pod安全；
- 默认不启用跨集群网络互通；
- 默认不允许GPU超额分配；
- 默认不允许本地存储承载无副本关键数据；
- 默认不安装Service Mesh和分布式存储；
- 专家能力按项目、集群或插件逐步启用。

---

## 5.7 租户与组织解耦

- 组织部门是人员和行政归属，不直接作为云资源隔离边界；
- 租户是资源所有权、安全、配额、成本和审计边界；
- 组织部门与租户采用多对多关联；
- 项目必须且只能归属一个租户；
- 用户权限由组织成员身份、租户角色、项目角色和资源策略共同计算；
- 跨租户共享默认禁止，必须经过显式授权、期限限制和审计；
- 租户级查询、缓存、事件和审计数据必须携带不可伪造的Tenant ID。

## 5.8 部署拓扑可组合

平台必须支持以下渐进式部署：

1. 单节点All-in-One；
2. 多节点管理计算融合高可用；
3. 管理节点与计算节点分离高可用；
4. 管理、计算、存储、GPU和可观测节点专用化；
5. 单网络、双网络、三网络和附加容灾网络；
6. 单中心、同城双活、异地灾备和多地域部署。

不同部署模式共享同一产品API、安装包和运维体系，避免形成多套产品分支。

## 5.9 安全能力分层

安全体系分为：

```text
身份与权限
→ 镜像和软件供应链
→ 准入和配置安全
→ 网络与数据安全
→ 容器运行时安全
→ 安全事件与审计
```

安全探针和扫描器通过Provider接入，核心平台负责策略、结果、事件、处置和审计，不自研漏洞库或内核探针。

## 5.10 容灾能力分层

- 本地高可用解决单节点和单组件故障；
- 同城双活解决机房级故障并追求较低RPO/RTO；
- 异地灾备解决区域级灾难；
- 多地域双活解决跨地域持续服务；
- Karmada只负责资源传播与跨集群调度，不能替代数据复制、全局流量和应用一致性；
- 所有自动切换必须具备健康判定、防抖、隔离、仲裁和防脑裂机制。

## 6.7 部署拓扑

### 6.7.1 单节点All-in-One

适用于开发、演示、小规模边缘和功能验证：

```text
单节点
├── Kubernetes控制面
├── HNB平台核心
├── 计算工作负载
└── 可选本地数据库、存储和可观测组件
```

要求：

- 管理和计算角色可以融合；
- 支持单网卡和单网络；
- 可以使用本地存储；
- 明确标记为非高可用模式；
- 不得将单节点故障恢复时间作为生产SLA承诺；
- 支持后续扩展为多节点模式，但应提供迁移和备份方案。

### 6.7.2 管理计算融合高可用

适用于资源规模有限但需要生产高可用的场景：

```text
节点1：管理 + 计算
节点2：管理 + 计算
节点3：管理 + 计算
```

要求：

- 管理控制面至少三个实例或等价仲裁能力；
- 平台核心、数据库和缓存跨节点分布；
- 业务工作负载可以运行在管理节点；
- 支持通过污点、优先级和资源预留保护管理组件；
- 管理组件资源不足时优先驱逐普通业务负载；
- 有状态服务根据存储和副本条件部署。

### 6.7.3 管理计算分离高可用

适用于中大型生产和集团平台：

```text
管理节点池：Kubernetes控制面、HNB核心、Karmada、平台数据库
计算节点池：业务应用
数据节点池：数据库和中间件
存储节点池：Rook-Ceph或本地存储
GPU节点池：整卡、MIG或HAMi
可观测节点池：日志、指标和链路后端
```

要求：

- 管理节点默认不承载普通租户工作负载；
- 计算、数据、存储、GPU和可观测节点池可以按需合并；
- 节点角色通过标签、污点、容忍和拓扑策略实现；
- 各节点池独立配置资源预留、超售、升级和维护策略；
- 管理节点故障不直接影响业务数据面；
- 计算节点扩缩容不要求重启平台控制面。

### 6.7.4 多地域管理部署

Enterprise模式支持：

- 两个或多个地域部署Agent Gateway和访问入口；
- 无状态API跨站点活动；
- 元数据存储采用明确的单写、主从或分布式一致性策略；
- Operation Engine使用领导者选举和围栏；
- 发生站点故障时可以切换管理入口；
- 避免两个站点同时执行互斥灾备操作。

### 6.7.5 部署模式能力矩阵

| 能力 | 单节点 | 融合高可用 | 分离高可用 | 多地域 |
|---|---:|---:|---:|---:|
| 管理与计算融合 | 支持 | 支持 | 可选 | 可选 |
| 核心服务多副本 | 否 | 是 | 是 | 是 |
| 管理网独立 | 可选 | 可选 | 推荐 | 推荐 |
| 存储网独立 | 可选 | 可选 | 推荐 | 推荐 |
| 业务网独立 | 可选 | 可选 | 推荐 | 推荐 |
| 站点级容灾 | 否 | 否 | 可扩展 | 支持 |
| 生产SLA | 不承诺HA | 可承诺 | 推荐模式 | 灾备增强 |

## 6.8 网络平面部署

### 6.8.1 网络平面定义

| 网络 | 主要流量 |
|---|---|
| 管理网 | 平台API、Kubernetes API、Agent、节点管理、证书和运维 |
| 存储网 | CSI、Ceph复制、数据库复制、备份和大数据IO |
| 业务网 | Pod业务流量、Service、Ingress/Gateway和外部访问 |
| 容灾网 | 跨站点数据复制、备份传输、灾备控制和演练流量 |

### 6.8.2 支持模式

#### 单网统一

所有流量共享一个物理或逻辑网络，适用于单节点、小规模和资源受限环境。

#### 管理与业务双网

管理流量独立，存储和业务共享，适用于一般生产。

#### 管理、存储和业务三网分离

三个网络使用独立VLAN、子网、网卡或Bond，适用于数据库、中间件和存储负载较重的生产环境。

#### 四网模式

在三网基础上增加容灾复制网络，适用于双活和异地灾备。

### 6.8.3 NetworkPlaneProfile

平台定义`NetworkPlaneProfile`，描述：

- 网络平面名称和用途；
- VLAN、子网和网关；
- 绑定网卡或Bond；
- MTU；
- 路由和防火墙；
- 是否允许跨租户；
- 带宽和QoS；
- 监控和告警；
- 故障切换链路；
- 是否用于备份或复制。

### 6.8.4 网络平面要求

1. 安装前检查网卡、VLAN、路由、MTU和地址冲突；
2. 支持单网卡、多网卡和Bond；
3. 支持通过Multus或等价机制为Pod挂载附加网络；
4. 管理网不可被普通租户直接访问；
5. 存储网默认禁止普通业务访问；
6. 业务网和管理网共享时必须通过策略隔离；
7. 网络平面分离不得改变上层应用API；
8. 网络配置变更支持预检、审计和回滚；
9. 双活复制流量应避免与在线业务争抢带宽；
10. 平台必须展示各网络平面的连通、时延、丢包和带宽状态。

## 6.9 双活与灾备技术架构

```text
                     全局DNS/GSLB/流量管理
                              │
               ┌──────────────┴──────────────┐
               │                             │
          站点A/Region A                 站点B/Region B
     HNB API/Agent Gateway           HNB API/Agent Gateway
          K8s集群A                        K8s集群B
     应用副本/数据副本               应用副本/数据副本
               │                             │
               └──────复制、仲裁、监控───────┘
                              │
                       异地灾备站点C
```

容灾由四个相互独立的层次组成：

1. **应用资源层**：使用Karmada或其他Provider传播无状态工作负载和配置；
2. **数据层**：使用数据库、中间件、CSI、对象存储或专用复制机制；
3. **流量层**：使用GSLB、DNS、全局网关或Service Mesh切换入口；
4. **管理控制层**：统一管理健康、策略、演练、切换、回切和审计。

平台不得把“工作负载已经分发到两个集群”等同于“业务已经实现双活”。

- 插件ID、版本、供应商和许可证；
- 平台API兼容版本；
- 能力声明；
- 配置Schema；
- CRD和权限清单；
- 网络访问清单；
- 主机目录和设备访问清单；
- 资源建议；
- 健康检查；
- 监控和告警模板；
- 升级、回滚和卸载脚本；
- 数据迁移说明；
- 签名和SBOM；
- 用户文档；
- 兼容矩阵。

## 8.3 插件隔离

- 独立Namespace；
- 独立ServiceAccount；
- 最小RBAC；
- 独立网络策略；
- CPU和内存限额；
- 必要的主机权限必须显式声明；
- 禁止访问其他插件数据库；
- 禁止绕过平台权限；
- 插件故障不导致核心重启；
- 插件升级可独立执行；
- 插件出站访问可审计；
- 特权DaemonSet必须经过安全审批。

→ 验证

### 所有权规则

- 组织单元不直接拥有Kubernetes资源；
- 租户是资源和安全边界；
- 项目必须属于一个租户；
- 环境、应用和服务实例继承项目的Tenant ID；
- 资源查询必须显式携带Tenant ID；
- 跨租户共享不得改变资源原始所有者。

## 10.4 Karmada联邦集群

### 10.4.1 定位

Karmada作为独立Federation Provider提供跨集群资源编排，不替代平台原有的集群资产管理和Agent通道。

```text
平台集群管理
├── 普通纳管集群
└── Karmada联邦
    ├── 成员集群
    ├── 传播策略
    ├── 差异化配置
    ├── 副本调度
    └── 故障转移
```

### 10.4.2 需求

| FED-03 | P1 | 支持Push和Pull两种成员集群接入模式。 |
| FED-04 | P1 | 私有网络、边缘和NAT环境优先使用Pull模式。 |
| FED-05 | P1 | 支持PropagationPolicy和ClusterPropagationPolicy管理。 |
| FED-06 | P1 | 支持按集群、标签、地域、架构和容量选择目标集群。 |
| FED-07 | P1 | 支持副本静态权重、动态权重、均匀和聚合分布。 |

### 10.4.3 联邦边界

1. Karmada负责资源传播和调度，不默认解决跨集群Pod网络互通；
2. 跨集群网络通过独立Multi-Cluster Network Provider实现；
3. 跨集群流量通过DNS、全局负载均衡、网关或服务网格插件实现；
4. 有状态应用跨集群迁移必须同时满足数据复制、备份恢复或外部共享存储条件；
5. 不允许仅凭Deployment迁移宣称数据库零数据丢失；
6. 故障转移前必须检查目标集群网络、存储、镜像和配额能力；
7. Karmada不可用时，成员集群上已分发工作负载继续运行。

## 10.6 容器网络

### 10.6.1 网络架构

平台采用CNI标准和Network Provider抽象：

```text
NetworkProfile
→ Network Provider
→ CNI插件
→ 路由/IPAM/策略/负载均衡
→ Hubble或同类网络可观测
```

推荐策略：

| 场景 | 推荐 |
|---|---|
| 标准和企业生产 | Cilium Provider |
| 复杂子网、VLAN、固定IP和OVN体系 | Kube-OVN Provider |
| 传统BGP和兼容场景 | Calico Provider |
| Minimal或兼容模式 | Flannel Provider |
| 多网卡和高性能网络 | Multus + SR-IOV/DPDK插件 |

Flannel模式若不具备网络策略执行能力，平台必须明确标记为“基础网络模式”，并配置额外策略插件或限制用于低安全场景。

### 10.6.3 网络性能要求

- 平台不得声称某CNI在所有环境下性能最优；
- 安装前检查内核、网卡、MTU和路由能力；
- 支持开启或关闭kube-proxy替换；
- 高性能模式需单独压测吞吐、P99时延、连接建立和CPU占用；
- 网络加密、高级L7策略和可观测功能的开销必须单独展示；
- SR-IOV和DPDK工作负载使用独立节点池和安全策略。

### 10.6.4 网络可靠性

- CNI升级前执行兼容性和连通性检查；
- CNI升级必须支持滚动和回滚；
- 网络控制组件多副本；
- 网络策略变更支持预检；
- 支持节点到节点、Pod到Pod、Pod到Service、DNS和外部网络诊断；
- 不允许因控制台不可用影响现有网络转发。

### 10.7.5 本地存储可靠性约束

本地存储具备高性能，但数据与节点绑定。平台必须：

1. 明确显示“节点故障可能导致卷不可用”；
2. 不将单副本本地卷默认标记为高可用；
3. 关键数据库必须依靠数据库自身复制或上层数据复制；
4. 节点维护前检查本地卷和有状态应用；
5. 禁止自动驱逐无法在其他节点恢复的数据；
6. 提供备份到对象存储的建议和策略；
7. 跨集群迁移必须先完成数据复制或恢复。

### 10.7.7 备份与恢复

- CSI快照不等同于异地备份；
- 支持卷快照、应用一致性备份和对象存储备份；
- 数据库备份应使用数据库原生能力；
- 中间件备份使用Provider声明的机制；
- 支持备份保留、加密、校验和恢复演练；
- 跨集群恢复需完成StorageClass和拓扑映射；
- 支持恢复到新卷，避免直接覆盖生产卷；
- 备份元数据不与业务数据保存在同一故障域。

### 10.8.4 GPU安全与可靠性

1. GPU驱动、运行时和插件版本必须纳入兼容矩阵；
2. 驱动升级必须支持节点级灰度；
3. GPU插件需要的特权权限必须显式展示；
4. 默认禁止显存超额分配；
5. 实验性超分功能必须单独开关并明确风险；
6. 关键任务默认使用整卡或硬件隔离；
7. vGPU任务必须验证显存限制是否生效；
8. GPU异常节点自动停止新任务调度；
9. 节点维护前检查GPU任务可迁移性；
10. 平台应区分“资源配额”和“运行时硬隔离”；
11. 使用共享GPU时，平台必须展示性能干扰风险；
12. GPU使用和分配必须进入审计和计量。

- GPU资源套餐；

- 显存；
- 算力比例；
- 共享或独占；
- 优先级。

高级设置包括：

- 设备型号；
- 节点池；
- 拓扑；
- 调度策略；
- MIG；
- DRA DeviceClass；
- HAMi设备参数。

### 10.15.4 管理控制面双活

平台管理面支持扩展为：

- 两站点API和Agent Gateway同时提供服务；
- 统一入口通过GSLB或DNS路由；
- 平台元数据采用明确的写入领导者和复制策略；
- Operation Engine使用全局锁、领导者选举和围栏；
- 站点切换期间禁止两个控制面同时执行互斥变更；
- 控制面灾备不依赖被管理业务集群；
- 管理面切换不应中断工作集群上的业务数据面。

### 10.15.5 容灾边界

1. Karmada解决工作负载分发，不自动解决数据一致性；
2. CSI快照解决时间点副本，不等同于异地备份；
3. 双集群运行不等同于双活，必须具备流量、数据和健康机制；
4. 自动切换只适用于完成演练并满足就绪检查的保护组；
5. 不支持自动切换的组件必须明确显示人工步骤；
6. 每个Provider必须声明真实RPO、RTO、复制方式和一致性级别。

## 11.2 网络安全

- 默认拒绝跨项目访问；
- 管理网络、存储网络、业务网络和备份网络可分离；
- CNI权限和主机网络能力最小化；
- 跨集群网络默认关闭；
- Egress访问可控制和审计；
- 网络策略修改支持影响预览；
- SR-IOV和DPDK节点执行专用安全策略。

## 11.3 存储安全

- CSI凭据不得暴露给普通用户；
- StorageClass敏感参数由管理员维护；
- 支持静态和传输加密能力声明；
- 删除策略和回收策略明确展示；
- 快照、备份和恢复操作审计；
- 本地磁盘回收前执行安全擦除策略；
- 跨租户禁止共享未授权卷和快照。

## 11.4 GPU安全

- GPU插件特权权限必须展示；
- 设备文件访问最小化；
- 驱动和运行时镜像可信；
- vGPU限制需要运行时验证；
- 共享任务之间的隔离等级必须声明；
- GPU任务和设备分配进入审计；
- 禁止普通用户修改节点级HAMi配置；
- 驱动升级使用专用维护流程。

## 11.5 联邦安全

- Karmada控制面使用独立证书和最小权限；
- 成员集群凭据加密保存和自动轮换；
- Push模式限制控制面访问范围；
- Pull模式Agent只访问必要资源；
- PropagationPolicy和OverridePolicy变更审计；
- 跨集群Secret传播默认禁止或需显式授权；
- 联邦策略不得绕过项目权限；
- 联邦控制面和平台控制面的角色边界清晰。

## 11.6 多租户安全

- API层强制注入Tenant Context；
- 数据库查询默认包含Tenant ID条件；

- 租户注销前检查数据、备份、快照、日志和审计保留要求。

## 11.7 容器运行时安全

### 11.7.1 推荐实现

平台通过`Runtime Security Provider`接入成熟开源组件：

- **Falco**：默认参考实现，用于监控Linux内核事件、容器和Kubernetes上下文并基于规则产生实时告警；
- **Tetragon**：可选eBPF增强实现，用于进程、系统调用、文件和网络安全可观测及受控执行响应。

Falco和Tetragon均不得成为不可替换的内核依赖。平台负责统一策略、事件、例外、响应和审计。

# 12. 可靠性需求

## 12.1 平台控制面

1. API、Controller、Worker和Agent Gateway多副本；
2. 单实例故障不影响平台服务；
3. PostgreSQL、Valkey和对象存储高可用；
4. 支持优雅关闭和连接排空；
5. Operation状态持久化；
6. Worker故障后任务可接管；
7. 插件故障不扩散；
8. 外部依赖故障时明确降级；
9. 控制面重启不影响工作负载；
10. 配置、数据库和密钥元数据定期备份；
11. 至少每半年执行恢复演练。

## 12.2 Agent

1. Agent断连不影响业务；
2. 本地缓存状态和结果；
3. 恢复后增量同步；
4. 周期全量校准；
5. Agent滚动升级；
6. Agent资源异常不拖垮节点；
7. 任务幂等和去重；
8. Agent证书自动轮换。

## 12.3 网络

- CNI控制组件高可用；
- CNI故障不影响已有内核转发表的基本转发，能力依实现验证；
- 网络升级支持灰度和回滚；
- 支持连通性持续探测；
- 支持DNS和Service故障快速定位；
- 高风险策略变更支持预检。

## 12.4 存储

- 第三方CSI能力和SLA由Provider声明；
- 核心数据不得仅依赖单节点本地盘；
- 快照与异地备份分开管理；
- 支持恢复有效性校验；
- 存储故障不会阻塞平台控制面；
- 磁盘满和高延迟提前告警。

## 12.5 GPU

- GPU设备健康检测；
- 异常设备停止调度；
- GPU节点维护支持排空策略；
- vGPU共享任务发生OOM时应按实现能力验证隔离；
- 驱动升级前检查运行任务；
- 整卡任务和共享任务使用独立资源池时互不影响。

## 12.6 联邦

- Karmada控制面高可用；
- Karmada故障不停止成员集群现有业务；
- 故障转移设置冷却和防抖；
- 避免网络抖动导致反复迁移；
- 优雅驱逐等待目标副本健康；
- 有状态服务迁移前检查数据条件；
- 联邦策略变更支持回滚。

---

## 12.7 部署拓扑可靠性

- 单节点模式明确展示单点风险；
- 融合高可用模式为管理组件预留CPU、内存和磁盘；
- 分离模式下管理节点不依赖计算节点上的普通应用；
- 管理节点至少跨三个故障域或满足仲裁要求；
- 网络平面统一部署时评估带宽竞争和故障影响；
- 三网分离时持续监测跨网路由和MTU；
- 管理、存储和业务网络任一故障应提供明确降级状态；
- 节点角色变更支持预检和回滚。

## 12.8 双活与灾备可靠性

- 保护组必须定期执行就绪检查；
- 自动切换只对通过最近演练的保护组开放；
- 切换设置防抖、冷却和最大重试次数；
- 复制延迟超过RPO时禁止无提示自动切换；
- 数据服务使用Provider提供的仲裁和防脑裂机制；
- 流量切换前确认目标端应用和数据健康；
- 回切前完成数据反向同步和冲突检查；
- 灾备控制面故障不影响当前业务站点运行；
- 关键灾备元数据和运行记录需要异地保存；
- 每年至少执行一次站点级综合演练，关键系统可提高频率。

## 13.2 建议规模基线

| 级别 | 管理集群 | 节点总数 | 工作负载实例 | 资源对象 |
|---|---:|---:|---:|---:|
| 基础验收 | 20 | 1,000 | 20,000 | 200,000 |
| 标准生产 | 50 | 5,000 | 100,000 | 1,000,000 |
| 扩展目标 | 200 | 20,000 | 500,000 | 5,000,000 |

联邦集群、GPU设备、存储卷、租户数量、组织关联和审批并发应单独压测，不能仅以Pod数量推断平台容量。

建议基础验收同时覆盖不少于100个租户、500个组织单元、1,000条租户组织关联和100个并发资源申请。

## 13.3 API目标

| 指标 | 目标 |
|---|---:|
| 普通查询API P95 | ≤500 ms |
| 普通查询API P99 | ≤2 s |
| 写操作受理 | ≤1 s并返回Operation ID |
| 控制台首屏 | ≤3 s |
| 常规状态可见延迟 | ≤10 s |
| 关键告警可见延迟 | ≤5 s |
| Agent重连开始同步 | ≤30 s |
| Operation进度更新 | ≤2 s或按步骤 |

## 13.4 性能约束

- 列表查询不实时访问所有集群；
- 使用Informer/Watch增量同步；
- Agent侧批量、压缩和去重；
- 大文件和备份流式传输；
- API分页、过滤和字段选择；
- 外部调用设置超时、连接池和熔断；
- 网络、存储和GPU性能使用专项基准测试；
- 不以控制面性能指标代替数据面性能指标。

# 14. 轻量化要求

## 14.1 核心资源目标

- Minimal核心建议控制在2 vCPU、4 GiB内存范围；
- 外部数据库、可观测存储和业务插件不计入核心；
- Agent默认目标不高于100m CPU、256 MiB内存；
- Karmada、HAMi、Rook-Ceph、Falco和Tetragon按部署档位和需求安装；
- 插件资源单独核算；
- 未使用插件可停用或缩容；
- 前端只加载有权限的插件模块；
- 日志、链路和网络流支持采样；
- 可观测后端可复用企业现有系统。

## 14.2 轻量化架构约束

- 核心不依赖消息大集群才能启动；
- 小规模可使用PostgreSQL Outbox作为内部事件机制；
- 不默认安装Service Mesh；
- 不默认安装分布式存储；
- 不强制Karmada管理所有集群；
- 不为少量GPU节点安装复杂批处理调度系统；
- 单一插件故障不要求重启整个平台；
- 单节点模式允许使用内置轻量依赖，高可用模式支持切换到外部高可用服务；
- 审批流程默认使用内置轻量状态机，不强制部署BPM引擎；
- 容灾组件只在启用灾备的站点安装。

# 20. 建设边界与最终原则

1. **不重复实现基础软件内核**  
   网络、存储、数据库、中间件和GPU虚拟化优先使用成熟组件。

2. **平台核心保持轻量**  
   Karmada、HAMi、Rook-Ceph和Service Mesh均按需安装。

3. **多集群纳管不等于联邦**  
   普通管理使用Agent；跨集群调度使用Karmada。

4. **资源调度不等于业务容灾**  
   跨集群迁移必须同时考虑数据、网络、入口和依赖。

5. **本地高性能不等于高可用**  
   本地盘必须结合应用复制和备份。

6. **共享GPU不等于完全独占隔离**  
   平台必须声明隔离等级、性能干扰和兼容性。

7. **插件化不等于无限拆分微服务**  
   核心可以模块化单体起步，插件必须具备独立故障域。

8. **极致性能来自架构和测试**  
   优先增量同步、状态本地化、异步任务、流式传输和背压，再使用Rust优化热点。

9. **简单易用来自产品抽象**  
   用户选择服务套餐，平台处理CNI、CSI、GPU和Karmada细节。

10. **可靠性优先于功能数量**  
    新插件必须同时具备监控、升级、备份、安全、诊断和回滚能力，才可标记为生产可用。

11. **组织不等于租户**  
    组织描述人员关系，租户描述云资源和安全边界，二者通过多对多关系关联。

12. **单节点可用不等于高可用**  
    单节点用于轻量场景；生产环境应根据SLA选择融合或分离高可用。

13. **网络统一和分离均为一等能力**  
    平台不得强制要求多网，也不得阻止高安全、高性能场景进行管理、存储和业务网络分离。

14. **扫描不等于运行时防护**  
    镜像安全负责部署前和存量风险，运行时安全负责执行行为和威胁事件，两者必须关联。

15. **备份不等于双活**  
    双活必须同时具备应用、数据、流量、仲裁、监控和演练能力。

| TenantOrgBinding | 租户与组织部门的多对多关联对象 |
| ResourceRequest | 容器、数据库或中间件服务申请单 |
| ApprovalPolicy | 资源申请的自动或人工审批规则 |
| NetworkPlaneProfile | 管理、存储、业务和容灾网络平面定义 |
| DRProtectionGroup | 具有统一RPO/RTO和恢复顺序的应用与数据集合 |
| DRPlan/DRRun | 灾备计划及一次演练、切换或回切执行记录 |
