# 云原生平台需求规格说明书（核心平台版）

> 文档版本：V2.0  
> 文档状态：评审优化稿  
> 输入依据：《需求规格说明书_云原生平台_v1.xlsx》  
> 本期范围：容器集群服务、应用管理、数据库服务、中间件服务、微服务治理、全链路可观测与运维、安全治理  
> 本期排除：DevOps研发过程与持续交付体系、AI算力与MaaS业务能力

---

## 1. 文档目的

本文档用于定义一套面向企业生产环境的云原生平台需求。平台以 Kubernetes 为主要资源编排底座，向上提供容器集群、应用、数据库、中间件、微服务和可观测运维等标准化服务。

本期建设重点不是覆盖尽可能多的功能，而是建立一个：

- **可靠**：控制面高可用，故障不扩散，数据面可独立运行；
- **可扩展**：微内核、插件化、Provider 化，能力可独立演进；
- **安全**：统一身份、最小权限、零信任、供应链和审计闭环；
- **轻量**：核心依赖少、资源占用可测、按需启用业务能力；
- **简单易用**：以应用和服务为中心，屏蔽底层 Kubernetes 复杂度；
- **高性能**：快慢路径分离、增量状态同步、异步长任务和数据本地化。

## 2. 原需求表评审结论

### 2.1 原表概况

原表共包含 **137 条需求**：

| 维度 | 数量 |
|---|---:|
| P0 | 68 |
| P1 | 47 |
| P2 | 22 |
| DevOps持续交付 | 12 |
| AI算力与模型服务 | 14 |
| 总体架构原则 | 18 |
| 容器集群服务 | 21 |
| 全链路可观测与智能运维 | 17 |

### 2.2 主要问题

1. **范围过宽**  
   容器平台、DBaaS、消息中间件、DevOps、研发管理、测试管理、AI算力、模型服务和知识库同时进入一期，容易形成“大而全但不深入”的平台。

2. **P0数量过多**  
   近一半需求被列为P0，无法体现真正的最小可用闭环，也不利于排期和验收。

3. **需求与实现方案混合**  
   需求描述中直接绑定 Karmada、KubeVela、Argo CD、Istio、KEDA 等实现，容易造成产品模型被具体开源组件反向限制。

4. **核心能力与插件能力边界不清**  
   数据库、中间件、服务网格、AI平台等能力被当作内核功能，和“微内核、轻量化”的总体目标存在冲突。

5. **部分指标缺乏验收前提**  
   “单集群150000 Pod”“不少于56项巡检”“不少于27项参数”等指标未明确硬件、网络、数据规模和测试模型，难以形成有效验收。

6. **重复建设风险明显**  
   容器、数据库、中间件、微服务分别建设监控告警，容易形成多个指标、日志和告警烟囱。

7. **过度依赖GitOps和服务网格**  
   GitOps、服务网格具有价值，但不应成为第一版平台使用的前置条件或内核强依赖。

8. **版本绑定过细**  
   将需求绑定某个 Kubernetes 或中间件具体小版本，会导致文档快速失效。应改为“兼容矩阵和 N/N-2 维护策略”。

## 3. 产品定位

### 3.1 产品定义

平台定位为：

> **面向企业应用全生命周期和基础服务运营的一体化云原生服务平台，通过统一控制面管理多个 Kubernetes 集群，并以插件方式提供数据库、中间件、微服务治理和可观测运维能力。**

平台不是 Kubernetes 对象管理控制台，也不是开源组件控制台集合。平台需要提供稳定的产品级抽象：

- 用户管理的是“项目、环境、应用和服务”；
- 平台负责转换和编排底层 Kubernetes、Operator、网络、存储和可观测资源；
- 底层实现可替换，上层产品模型保持稳定。

### 3.2 目标用户

| 用户角色 | 主要诉求 |
|---|---|
| 平台管理员 | 集群纳管、插件管理、平台配置、容量、安全和审计 |
| 运维人员 | 监控、告警、巡检、诊断、备份、恢复、扩缩容和升级 |
| 项目管理员 | 成员、配额、环境、应用和服务实例管理 |
| 应用运维人员 | 应用部署、配置、日志、链路、告警、扩缩容和回滚 |
| 安全审计人员 | 权限审查、风险发现、操作审计和合规报告 |
| 开发使用者 | 通过简单目录申请数据库、中间件和应用运行资源 |

## 5. 总体设计原则

### 5.1 微内核

平台内核只保留不可缺少的通用能力：

1. 统一API入口；
2. 组织、项目和环境模型；
3. 资源目录与统一资源标识；
4. Operation长任务和状态机；
5. 插件注册与生命周期管理；
6. 权限、策略和审计；
7. 集群Agent连接和任务分发；
8. 事件总线与状态快照。

数据库、中间件、服务网格、可观测后端等均不得编译进入核心二进制。

### 5.2 控制面与数据面分离

- 中心控制面负责配置、编排、治理和状态聚合；
- 工作集群负责应用、数据库和中间件实际运行；
- 控制面故障不得影响已运行数据面业务；
- Agent断连时，工作集群应继续执行 Kubernetes 和 Operator 本地自治；
- 控制面恢复后通过增量同步和周期校准恢复一致状态。

### 5.3 产品模型与实现解耦

平台定义统一领域对象：

- Organization
- Project
- Environment
- Cluster
- Application
- Component
- ServiceInstance
- ServiceBinding
- Release
- Operation
- Alert
- Plugin

不得将 Deployment、StatefulSet、CRD 等原始 Kubernetes 对象直接作为唯一产品模型。

### 5.4 声明式和幂等

- 所有资源创建和变更必须描述期望状态；
- Controller持续对比期望状态和实际状态；
- 所有操作必须支持幂等、超时、重试和最终一致性校准；
- API重复提交不得创建重复实例；
- 长任务不得依赖同步HTTP连接完成。

### 5.5 快慢路径分离

**快路径**用于资源列表、详情、拓扑和当前状态查询，只读取中心快照、缓存或查询模型，不同步访问远端集群。

**慢路径**用于创建、升级、扩容、备份和恢复，统一生成Operation并异步执行，通过SSE或WebSocket推送进度。

## 7. 插件化体系要求

### 7.1 插件类型

| 类型 | 说明 |
|---|---|
| Resource Provider | 对接集群、数据库、中间件、云资源 |
| Controller Plugin | 实现领域对象调和和生命周期控制 |
| UI Plugin | 向统一控制台提供可选页面 |
| Observability Plugin | 提供采集规则、看板和告警模板 |
| Policy Plugin | 提供准入、安全和治理规则 |
| Integration Plugin | 对接IAM、CMDB、ITSM、SIEM和通知渠道 |

### 7.2 插件包组成

每个插件包至少包含：

- `plugin.yaml`插件描述；
- 插件ID、版本、供应商和许可证；
- 平台API兼容版本；
- 能力声明；
- 安装、升级、回滚和卸载脚本；
- 所需CRD和权限清单；
- 网络访问清单；
- 资源配额建议；
- 健康检查接口；
- 可观测指标和告警模板；
- 数据迁移说明；
- 签名和SBOM；
- 用户文档。

### 7.3 插件隔离

- 插件必须以独立进程或独立容器运行；
- 每个插件使用独立ServiceAccount和最小RBAC权限；
- 插件默认部署到独立Namespace；
- 插件之间禁止直接访问对方数据库；
- 插件只能通过公开契约、gRPC/HTTP API或事件总线通信；
- 插件故障、升级和卸载不得导致核心控制面重启；
- 插件资源超限不得拖垮平台内核；
- 插件数据库应采用独立Schema或独立实例；
- 插件出站访问必须可配置和可审计。

### 7.4 生命周期

插件生命周期必须支持：

```text
上传/注册 → 签名校验 → 兼容性检查 → 权限预览
→ 安装 → 健康验证 → 启用
→ 升级/灰度 → 验证 → 完成或回滚
→ 禁用 → 卸载 → 数据保留或清理
```

### 7.5 兼容性

- 插件版本使用语义化版本；
- 平台维护兼容矩阵；
- API至少保留一个大版本的兼容窗口；
- 破坏性变更必须提供迁移工具；
- 核心升级前必须检测全部已安装插件；
- 不兼容插件不得被静默升级。

## 8. 用户与资源模型

平台面向普通用户只呈现四级模型：

```text
组织
└── 项目
    └── 环境
        ├── 应用
        └── 服务实例
```

### 8.1 组织

用于集团、子公司或部门级隔离和授权。

### 8.2 项目

用于成员、配额、集群范围、成本和资源权限隔离。

### 8.3 环境

用于开发、测试、生产或用户自定义环境。底层可映射至命名空间或命名空间集合。

### 8.4 应用

应用由一个或多个组件构成，并关联配置、密钥、网关、数据库、中间件、告警和SLO。

### 8.5 服务实例

服务实例包括数据库、中间件、网关、配置中心等平台托管服务。

### 9.3.1 Kubernetes版本策略

- 平台不得绑定单一小版本；
- 维护明确的认证兼容矩阵；
- 原则上支持当前主版本及前两个次版本；
- 每个版本必须经过安装、升级、网络、存储、监控和安全回归测试；
- 超出支持范围的集群允许只读纳管，但应显示风险提示。

## 11. 可靠性需求

### 11.1 控制面

1. 核心API、Controller、Worker和Agent Gateway支持多副本部署；
2. 单实例故障不得导致管理服务不可用；
3. 数据库、缓存和对象存储应支持高可用部署或使用外部高可用服务；
4. 所有核心服务支持优雅关闭和连接排空；
5. 关键操作必须持久化步骤和执行状态；
6. Worker故障后任务可被其他实例恢复执行；
7. 插件异常不得产生核心级联故障；
8. 外部依赖不可用时，核心API应返回缓存数据或明确降级状态；
9. 控制面重启后不得要求重新部署工作集群应用；
10. 平台配置和元数据支持定期备份与恢复演练。

### 11.2 Agent与工作集群

1. Agent断连期间工作集群继续运行；
2. Agent本地保存未上报事件和任务结果；
3. 恢复连接后执行增量同步；
4. 周期执行全量校准以修正丢失事件；
5. Agent升级支持滚动升级和失败回滚；
6. Agent资源异常不得影响节点业务工作负载；
7. Agent不得拥有超出管理范围的集群权限；
8. Agent任务必须支持去重和幂等。

### 11.3 故障域

- 支持节点、机架、可用区和Region拓扑标签；
- 核心组件和关键服务应跨故障域分布；
- 使用反亲和、拓扑分布和PodDisruptionBudget；
- 存储、网络和控制面故障应分别进行演练；
- 数据库和中间件的RPO/RTO由服务套餐明确声明。

---

## 12. 扩展性需求

1. 核心服务可水平扩展，不依赖本地会话；
2. 状态查询采用增量同步和Read Model，不对所有集群实时轮询；
3. Agent上报支持批量、压缩、背压和优先级通道；
4. 插件可独立扩缩容；
5. 支持新增Provider而不修改平台内核；
6. 支持在一个服务类型下注册多个实现；
7. 支持按Region部署Agent Gateway和遥测Gateway；
8. 支持按租户、项目和Region分片查询数据；
9. 高数据量审计、日志和指标使用专用存储；
10. 多集群联邦、边缘和多云能力通过插件扩展。

### 12.1 建议规模基线

首期验收建议采用分层目标，而不是直接采用Kubernetes理论极限：

| 级别 | 管理集群 | 节点总数 | 工作负载实例总数 |
|---|---:|---:|---:|
| 基础验收 | 20 | 1,000 | 20,000 |
| 标准生产 | 50 | 5,000 | 100,000 |
| 扩展目标 | 200 | 20,000 | 500,000 |

具体承诺必须绑定硬件、网络、数据库、可观测采样率和API压测模型。

## 13. 轻量化要求

### 13.1 部署档位

| 档位 | 适用场景 | 特征 |
|---|---|---|
| Minimal | 开发、演示、小规模 | 单副本核心，可使用外部数据库，不部署非必要插件 |
| Standard | 普通生产 | 核心高可用，统一监控，按需部署DB/MW插件 |
| Enterprise | 集团生产 | 多Region、专用可观测后端、灾备和安全增强 |

### 13.2 资源要求

- 未安装业务插件时，核心常驻资源必须有明确基准；
- Minimal模式核心服务建议控制在 **2 vCPU、4 GiB内存**范围，外部数据库和可观测存储不计入；
- Standard高可用模式应提供每组件资源建议和容量模型；
- 插件资源必须独立统计；
- 未使用的可选插件可停止或缩容；
- 仅无状态且允许冷启动的插件可Scale-to-Zero；
- 不得为了“统一平台”默认安装全部数据库、中间件和服务网格；
- 前端只加载当前用户有权访问的插件模块；
- Agent默认资源建议不高于单节点 **100m CPU、256 MiB内存**，特殊采集能力单独计量；
- 日志、链路和指标采集必须支持限速和采样。

> 上述资源值为需求目标，最终以原型压测结果确认。

## 15. 性能需求

### 15.1 API性能

在标准生产基线环境和定义负载下：

| 指标 | 目标 |
|---|---:|
| 普通查询API P95 | ≤500 ms |
| 普通查询API P99 | ≤2 s |
| 写操作受理响应 | ≤1 s，返回Operation ID |
| 控制台首屏核心数据 | ≤3 s |
| 状态变更可见延迟 | 常规≤10 s，关键告警≤5 s |
| Agent断线重连 | ≤30 s开始同步 |
| 关键操作进度推送 | ≤2 s更新一次或按步骤更新 |

### 15.2 性能架构约束

- 列表查询不得同步访问多个远端集群；
- 资源状态通过Informer/Watch增量获取；
- 高频事件在Agent侧去重和聚合；
- 大文件、备份和日志使用流式传输；
- API支持分页、过滤和字段选择；
- 所有外部依赖调用设置超时、连接池、熔断和并发上限；
- 查询与事务写模型可独立扩展；
- 大规模遥测查询不得与平台业务数据库共享热路径。

## 16. 数据与存储要求

| 数据类型 | 推荐存储 |
|---|---|
| 组织、项目、应用、服务实例 | PostgreSQL |
| Operation和状态机 | PostgreSQL |
| 热状态、会话和权限缓存 | Valkey |
| 资源状态快照 | PostgreSQL分区表或专用查询存储 |

### 16.1 数据一致性

- 数据库事务和事件发布采用Outbox或等价模式；
- 每个写请求具有唯一Request ID；
- Operation具有唯一幂等键；
- 资源删除采用终结器或等价状态机；
- 删除失败可继续恢复；
- 状态快照允许最终一致，但权限和审计必须强一致；
- 插件卸载前必须声明数据保留策略。

## 17. 开发语言与技术约束

### 17.1 推荐语言分工

| 模块 | 推荐语言 | 说明 |
|---|---|---|
| 平台API和微内核 | Go | Kubernetes生态成熟，适合控制面和并发I/O |
| Controller和Operator | Go | 优先使用controller-runtime/Kubebuilder体系 |
| Cluster Agent | Go | 复用Kubernetes Informer、Watch和类型系统 |
| CLI | Go | 单文件交付，跨平台方便 |
| 高吞吐流式代理 | Rust | 用于有明确压测收益的网络、日志、备份热路径 |
| 边缘轻量采集器 | Rust或Go | 资源极度受限时评估Rust |
| 前端 | TypeScript | 统一控制台和可选微前端插件 |

### 17.2 语言选择原则

- **Go负责控制、编排和Kubernetes集成；**
- **Rust负责经过性能剖析确认的热路径；**
- 不为追求技术标签将全部控制面Rust化；
- Rust模块必须通过稳定gRPC/Protobuf契约与Go控制面交互；
- 不使用Go原生动态`plugin`机制承载平台插件；
- 平台插件优先采用进程外服务或独立Controller；
- 公共API、事件和错误码必须语言无关。

### 17.3 推荐基础技术

| 领域 | 建议 |
|---|---|
| 外部API | REST/OpenAPI |
| 内部通信 | gRPC/Protobuf |
| 实时进度 | SSE，终端和双向交互使用WebSocket |
| 数据库 | PostgreSQL |
| 缓存 | Valkey |
| 对象存储 | S3兼容接口 |
| 应用编排 | Kubernetes Controller/Operator |
| 北南流量 | Gateway API兼容实现 |
| 网络隔离 | CNI NetworkPolicy |
| 遥测标准 | OpenTelemetry |
| 镜像标准 | OCI |
| 插件包 | OCI Artifact或签名软件包 |
| 策略 | 准入策略引擎，可插拔 |
| 密钥 | KMS/Vault类服务，可插拔 |

## 18. API与契约要求

### 18.1 API规则

- 对外API统一版本管理；
- API资源使用稳定领域名称；
- 所有写操作支持幂等请求头；
- 异步操作返回Operation；
- 错误响应包含错误码、可读消息、关联ID和处理建议；
- API权限与UI权限使用同一授权结果；
- API变更必须经过兼容性评审；
- 删除和破坏性操作必须显式确认。

### 18.2 插件契约

核心向插件提供：

- 插件注册；
- 身份和租户上下文；
- 权限校验；
- Operation创建和更新；
- 事件发布与订阅；
- Secret引用；
- 状态和健康上报；
- 审计记录；
- UI导航注册；
- 告警和看板注册。

插件不得依赖核心未公开的内部表结构。

## 19. 可运维性要求

1. 平台自身必须提供健康检查、就绪检查和启动检查；
2. 关键组件必须输出结构化日志；
3. 日志必须包含Trace ID、Request ID、Operation ID、插件ID和租户信息；
4. 提供平台依赖检查和一键巡检；
5. 支持生成脱敏诊断包；
6. 支持配置备份、数据库备份和恢复；
7. 支持平台版本升级前检查；
8. 核心升级支持滚动升级；
9. 数据库Schema升级必须支持失败恢复；
10. 插件升级与平台升级可独立执行；
11. 提供容量、证书、磁盘和版本到期预警；
12. 所有自动修复必须有白名单和最大影响范围；
13. 自动修复前后必须记录证据和结果；
14. 平台不得自动执行高风险不可逆修复。

## 20. 验收要求

### 20.1 架构验收

- 禁用任一业务插件，核心平台和其他插件仍正常；
- 安装新插件不要求重启核心；
- 插件不能访问未授权的其他插件数据；
- 更换数据库或中间件Provider不改变上层服务API；
- 控制面停机期间工作集群应用继续运行。

### 20.2 可靠性验收

至少执行：

- 核心API单实例故障；
- Controller/Worker实例故障；
- Agent断网和恢复；
- 插件异常退出；
- 平台数据库主备切换；
- 节点维护和Pod驱逐；
- 数据库服务主节点故障；
- 消息中间件节点故障；
- 对象存储短时不可用；
- 控制面整体重启；
- 配置备份和恢复演练。

### 20.3 安全验收

至少验证：

- 越权访问；
- 跨项目资源访问；
- 插件权限越界；
- 未签名镜像和插件准入；
- 高危漏洞镜像拦截；
- 密钥明文泄露检查；
- 审计日志完整性；
- mTLS证书轮换；
- NetworkPolicy隔离；
- 特权容器准入；
- 高风险操作二次确认。

### 20.4 性能验收

性能报告必须说明：

- 硬件和网络配置；
- 管理集群和节点数量；
- 资源对象数量；
- Agent上报频率；
- 指标、日志和链路采样率；
- 并发用户和请求模型；
- API P50/P95/P99；
- 数据库、缓存和消息组件配置；
- 测试持续时间；
- 错误率和资源峰值。

不得仅给出单次峰值TPS作为平台性能结论。

### 20.5 易用性验收

- 新用户在不编辑原生YAML的情况下完成应用部署；
- 新用户通过服务目录创建数据库并绑定应用；
- 用户可在一个应用页面定位日志、告警和调用链；
- 常见失败操作提供明确修复建议；
- 创建普通服务的必填字段不超过约定上限；
- 危险操作可明确看到影响范围和恢复方式。

## 22. 建设边界与最终原则

1. **不重复造基础软件内核**  
   数据库、中间件、网关和可观测存储应优先复用成熟开源或商业组件。

2. **平台价值在于统一产品模型和治理**  
   核心竞争力是服务目录、生命周期、可靠性、安全、服务绑定、统一拓扑和简单体验。

3. **插件化不是把所有功能都拆成微服务**  
   核心可采用模块化单体与少量独立服务起步，插件必须具备独立故障域和稳定契约。

4. **轻量化不等于功能少**  
   轻量化意味着最小核心、按需安装、合理默认值、可测资源占用和不强制依赖重型组件。

5. **极致性能首先来自架构**  
   优先采用状态本地化、增量同步、异步任务、流式传输、背压和数据分层，再针对真实热点使用Rust优化。

6. **可靠性优先于功能数量**  
   每增加一个服务插件，必须同步具备高可用、监控、备份、升级、安全和诊断能力，否则不得标记为生产可用。

## 附录A：核心需求优先级判定标准

| 优先级 | 定义 |
|---|---|
| P0 | 缺失会导致核心闭环不可用、无法生产运行或存在重大安全风险 |
| P1 | 生产增强能力，可在核心闭环后分批交付 |
| P2 | 高级、特定行业或可选扩展能力 |

## 附录B：关键术语

| 术语 | 定义 |
|---|---|
| 微内核 | 只包含最小公共能力的核心，业务能力通过插件接入 |
| Provider | 某类资源或服务的具体实现适配器 |
| Operation | 对长时间资源操作的持久化状态机 |
| Agent | 部署于受管集群，负责增量同步和任务执行的组件 |
| 服务绑定 | 将数据库或中间件凭据、安全策略和连接信息安全关联到应用 |
| 数据面 | 实际运行应用、数据库和中间件的工作集群 |
| 控制面 | 负责管理、编排、治理和状态聚合的平台服务 |
| Read Model | 面向查询优化的中心状态快照，避免实时轮询远端集群 |
