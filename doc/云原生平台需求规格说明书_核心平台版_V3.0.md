# 1. 文档目的

本文档定义一套面向企业生产环境的云原生平台需求和技术架构。平台以Kubernetes为核心资源编排底座，通过统一控制面管理多个异构集群，以插件方式提供容器网络、容器存储、GPU、数据库、中间件、微服务和可观测运维能力。

平台建设不追求将所有云原生项目简单集成到一个控制台，而是建立一个：

- **可靠的平台**：控制面高可用，数据面自治，故障不扩散，操作可恢复；
- **开放的平台**：遵循Kubernetes、CNI、CSI、OCI、OpenTelemetry等标准；
- **可扩展的平台**：微内核、插件化、Provider化，底层实现可以替换；
- **安全的平台**：统一身份、最小权限、零信任、供应链安全和审计闭环；
- **轻量的平台**：核心依赖少，功能按需安装，避免强制部署重型组件；
- **高性能的平台**：快慢路径分离，增量同步，数据本地处理，热点模块可使用Rust；
- **简单易用的平台**：以项目、环境、应用和服务为中心，屏蔽底层复杂性。

# 2. 输入材料评审与优化原则

## 2.1 对参考白皮书的吸收

参考白皮书中以下能力具有较高借鉴价值：

1. 统一管理多个Kubernetes集群和异构基础设施；
2. 通过项目和命名空间实现多租户隔离；
3. 支持Cilium、Calico、Kube-OVN等多种容器网络；
4. 支持外部存储、Rook-Ceph分布式存储和TopoLVM本地存储；
5. 通过Operator简化数据库、中间件和有状态服务管理；
6. 提供联邦集群、跨集群应用和灾备能力；
7. 支持整卡GPU和vGPU资源配置；
8. 提供监控、日志、事件、审计、巡检和告警；
9. 通过OperatorHub和应用目录降低扩展能力使用门槛。

## 2.2 不直接照搬的内容

以下设计不直接进入本期核心：

- DevOps工具链和持续集成；
- 强绑定Jenkins、Tekton、GitLab等工具；
- 默认强制安装Service Mesh；
- 将所有数据库、中间件和存储组件编译进核心；
- 将理论规模或其他产品测试结果直接作为本平台承诺；
- 将Karmada、HAMi、Cilium或Rook-Ceph设置为不可替换的内核依赖；
- 将所有Kubernetes原生对象直接暴露给普通用户。

## 2.3 核心优化原则

### 2.3.1 先建立核心闭环，再扩展生态

核心闭环包括：

```text
集群纳管
→ 项目与环境
→ 应用运行
→ 网络与存储
→ 监控与告警
→ 安全与审计
→ 数据库和中间件服务
```

联邦、多网络、GPU虚拟化、分布式存储和Service Mesh均以插件方式按需启用。

### 2.3.2 产品需求与具体实现分层

产品层定义稳定能力，例如：

- 集群；
- 网络配置；
- 存储配置；
- 加速器资源池；
- 联邦调度策略；
- 数据库实例；
- 中间件实例。

实现层可以使用Cilium、Kube-OVN、HAMi、Karmada或其他兼容组件，上层API和用户体验不因实现替换而变化。

# 3. 产品定位

## 3.1 产品定义

> **HNB Cloud是一套面向企业应用、容器、数据服务和中间件统一运营的云原生平台，通过微内核控制面、插件化能力中心和分布式集群Agent，实现多集群、多基础设施和多服务类型的统一管理。**

平台不是单纯的Kubernetes Dashboard，也不是多个开源控制台的入口集合。

普通用户主要管理：

```text
组织
└── 项目
    └── 环境
        ├── 应用
        ├── 数据库服务
        ├── 中间件服务
        └──网络、存储和GPU服务配额
```

平台自动处理：

- Kubernetes资源生成；
- 网络和存储绑定；
- GPU调度；
- 账号和凭据；
- 安全策略；
- 监控采集；
- 日志和链路；
- 备份和恢复；
- 跨集群传播与故障转移。

## 3.2 核心价值

| 价值 | 说明 |
|---|---|
| 统一资源底座 | 统一管理物理机、虚拟机、私有云、公有云和边缘Kubernetes集群 |
| 统一服务供给 | 通过服务目录提供数据库、中间件、网络、存储和GPU服务 |

# 5. 总体设计原则

## 5.1 微内核

平台核心只承担不可缺少的公共能力：

1. 统一API和身份上下文；
2. 组织、项目和环境；
3. 统一资源模型；
4. Operation异步操作引擎；
5. 插件注册和生命周期；
6. 权限、策略和审计；
7. 集群Agent连接和任务分发；
8. 事件总线；
9. 状态快照和资源关系图谱；
10. 配置、密钥引用和能力发现。

以下能力不得直接编译进核心：

- CNI；
- CSI；
- Karmada；
- HAMi；
- 数据库Operator；
- 中间件Operator；
- Service Mesh；
- 可观测存储；
- 云厂商API适配。

## 5.2 控制面与数据面分离

- 中心控制面负责配置、编排、治理和状态聚合；
- 工作集群负责应用、数据库、中间件、网络、存储和GPU实际运行；
- 控制面故障时，已运行数据面继续工作；
- 集群Agent断连时，Kubernetes和Operator继续本地调和；
- 控制面恢复后通过增量同步和周期校准恢复状态；
- 业务流量、数据库流量和消息流量不经过平台控制面。

## 5.3 普通多集群与联邦集群分离

### 普通多集群纳管

用于：

- 统一资产；
- 权限和项目管理；
- 监控与运维；
- 独立集群部署；
- 数据服务管理。

每个集群保持独立，不要求安装Karmada。

### Karmada联邦

用于：

- 同一应用跨集群部署；
- 跨地域副本分布；
- 集群故障迁移；
- 多云和混合云调度；
- 统一传播和差异化配置。

联邦能力是可选插件，不能成为单集群用户的部署前置条件。

## 5.4 声明式、幂等和最终一致

- 所有资源以期望状态描述；
- Controller持续调和期望状态和实际状态；
- 创建、升级、扩容、备份和恢复支持幂等；
- 所有长任务持久化状态；
- 操作失败后可重试、恢复、取消或补偿；
- API重复提交不得产生重复资源；
- 状态允许最终一致，权限和审计必须强一致。

## 5.5 快慢路径分离

### 快路径

- 资源列表；
- 当前状态；
- 应用拓扑；
- 告警和事件；
- 权限校验；
- 资源查询。

快路径只读取中心Read Model、缓存和查询存储，不实时遍历远端集群。

### 慢路径

- 集群创建；
- 插件安装；
- 网络和存储变更；
- 应用发布；
- 数据库和中间件创建；
- GPU驱动部署；
- Karmada传播；
- 备份恢复。

慢路径通过Operation异步执行，并使用SSE或WebSocket推送进度。

## 5.6 默认安全与渐进增强

- 默认启用基础网络隔离和Pod安全；
- 默认不启用跨集群网络互通；
- 默认不允许GPU超额分配；
- 默认不允许本地存储承载无副本关键数据；
- 默认不安装Service Mesh和分布式存储；
- 专家能力按项目、集群或插件逐步启用。

- 断网本地缓存；
- 恢复后断点续传；
- 任务幂等；
- 上报限速和背压；
- 支持高优先级事件通道；
- 不保存平台核心业务状态；
- 资源占用可控；
- 不暴露公网管理端口。

## 6.5 Provider架构

统一Provider接口建议包括：

```go
type Provider interface {
    Capabilities(ctx context.Context) (*CapabilitySet, error)
    Validate(ctx context.Context, req ResourceRequest) error
    Plan(ctx context.Context, req ResourceRequest) (*Plan, error)
    Apply(ctx context.Context, plan *Plan) (*OperationRef, error)
    Observe(ctx context.Context, ref ResourceRef) (*ResourceState, error)
    Upgrade(ctx context.Context, req UpgradeRequest) (*OperationRef, error)
    Backup(ctx context.Context, req BackupRequest) (*OperationRef, error)
    Restore(ctx context.Context, req RestoreRequest) (*OperationRef, error)
    Delete(ctx context.Context, ref ResourceRef) (*OperationRef, error)
}
```

Provider类型包括：

- Cluster Provider；
- Network Provider；
- Storage Provider；
- Accelerator Provider；
- Federation Provider；
- Database Provider；
- Middleware Provider；
- Gateway Provider；
- Observability Provider；
- Backup Provider。

## 6.6 操作处理流程

```text
用户提交请求
→ API校验身份、权限和幂等键
→ 策略引擎检查安全、配额和兼容性
→ Provider生成执行Plan
→ Operation Engine持久化操作
→ Agent或插件执行步骤
→ 状态持续回传
→ Read Model更新
→ SSE/WebSocket推送进度
→ 完成、回滚或等待人工处理
```

### 10.7.5 本地存储可靠性约束

本地存储具备高性能，但数据与节点绑定。平台必须：

1. 明确显示“节点故障可能导致卷不可用”；
2. 不将单副本本地卷默认标记为高可用；
3. 关键数据库必须依靠数据库自身复制或上层数据复制；
4. 节点维护前检查本地卷和有状态应用；
5. 禁止自动驱逐无法在其他节点恢复的数据；
6. 提供备份到对象存储的建议和策略；
7. 跨集群迁移必须先完成数据复制或恢复。

1. GPU驱动、运行时和插件版本必须纳入兼容矩阵；

9. 节点维护前检查GPU任务可迁移性；
10. 平台应区分“资源配额”和“运行时硬隔离”；
11. 使用共享GPU时，平台必须展示性能干扰风险；
12. GPU使用和分配必须进入审计和计量。

- 管理网络、存储网络、业务网络和备份网络可分离；

- 跨集群网络默认关闭；

- 网络策略修改支持影响预览；

## 11.3 存储安全

- CSI凭据不得暴露给普通用户；
- StorageClass敏感参数由管理员维护；

- 删除策略和回收策略明确展示；
- 快照、备份和恢复操作审计；
- 本地磁盘回收前执行安全擦除策略；
- 跨租户禁止共享未授权卷和快照。

## 11.4 GPU安全

- GPU插件特权权限必须展示；
- 设备文件访问最小化；
- 驱动和运行时镜像可信；
- vGPU限制需要运行时验证；
- 共享任务之间的隔离等级必须声明；
- GPU任务和设备分配进入审计；
- 禁止普通用户修改节点级HAMi配置；
- 驱动升级使用专用维护流程。

## 11.5 联邦安全

- Karmada控制面使用独立证书和最小权限；
- 成员集群凭据加密保存和自动轮换；
- Push模式限制控制面访问范围；
- Pull模式Agent只访问必要资源；
- PropagationPolicy和OverridePolicy变更审计；
- 跨集群Secret传播默认禁止或需显式授权；
- 联邦策略不得绕过项目权限；
- 联邦控制面和平台控制面的角色边界清晰。

# 12. 可靠性需求

## 12.1 平台控制面

1. API、Controller、Worker和Agent Gateway多副本；
2. 单实例故障不影响平台服务；
3. PostgreSQL、Valkey和对象存储高可用；
4. 支持优雅关闭和连接排空；
5. Operation状态持久化；
6. Worker故障后任务可接管；
7. 插件故障不扩散；
8. 外部依赖故障时明确降级；
9. 控制面重启不影响工作负载；
10. 配置、数据库和密钥元数据定期备份；
11. 至少每半年执行恢复演练。

## 12.2 Agent

1. Agent断连不影响业务；
2. 本地缓存状态和结果；
3. 恢复后增量同步；
4. 周期全量校准；
5. Agent滚动升级；
6. Agent资源异常不拖垮节点；
7. 任务幂等和去重；
8. Agent证书自动轮换。

## 12.3 网络

- CNI控制组件高可用；
- CNI故障不影响已有内核转发表的基本转发，能力依实现验证；
- 网络升级支持灰度和回滚；
- 支持连通性持续探测；
- 支持DNS和Service故障快速定位；
- 高风险策略变更支持预检。

## 12.4 存储

- 第三方CSI能力和SLA由Provider声明；
- 核心数据不得仅依赖单节点本地盘；
- 快照与异地备份分开管理；
- 支持恢复有效性校验；
- 存储故障不会阻塞平台控制面；
- 磁盘满和高延迟提前告警。

## 12.5 GPU

- GPU设备健康检测；
- 异常设备停止调度；
- GPU节点维护支持排空策略；
- vGPU共享任务发生OOM时应按实现能力验证隔离；
- 驱动升级前检查运行任务；
- 整卡任务和共享任务使用独立资源池时互不影响。

## 12.6 联邦

- Karmada控制面高可用；
- Karmada故障不停止成员集群现有业务；
- 故障转移设置冷却和防抖；
- 避免网络抖动导致反复迁移；
- 优雅驱逐等待目标副本健康；
- 有状态服务迁移前检查数据条件；
- 联邦策略变更支持回滚。

# 14. 轻量化要求

## 14.1 核心资源目标

- Minimal核心建议控制在2 vCPU、4 GiB内存范围；
- 外部数据库、可观测存储和业务插件不计入核心；
- Agent默认目标不高于100m CPU、256 MiB内存；
- Karmada、HAMi、Rook-Ceph不默认安装；
- 插件资源单独核算；
- 未使用插件可停用或缩容；
- 前端只加载有权限的插件模块；
- 日志、链路和网络流支持采样；
- 可观测后端可复用企业现有系统。

## 14.2 轻量化架构约束

- 核心不依赖消息大集群才能启动；
- 小规模可使用PostgreSQL Outbox作为内部事件机制；
- 不默认安装Service Mesh；
- 不默认安装分布式存储；
- 不强制Karmada管理所有集群；
- 不为少量GPU节点安装复杂批处理调度系统；
- 单一插件故障不要求重启整个平台。

# 20. 建设边界与最终原则

1. **不重复实现基础软件内核**  
   网络、存储、数据库、中间件和GPU虚拟化优先使用成熟组件。

2. **平台核心保持轻量**  
   Karmada、HAMi、Rook-Ceph和Service Mesh均按需安装。

3. **多集群纳管不等于联邦**  
   普通管理使用Agent；跨集群调度使用Karmada。

4. **资源调度不等于业务容灾**  
   跨集群迁移必须同时考虑数据、网络、入口和依赖。

5. **本地高性能不等于高可用**  
   本地盘必须结合应用复制和备份。

6. **共享GPU不等于完全独占隔离**  
   平台必须声明隔离等级、性能干扰和兼容性。

7. **插件化不等于无限拆分微服务**  
   核心可以模块化单体起步，插件必须具备独立故障域。

8. **极致性能来自架构和测试**  
   优先增量同步、状态本地化、异步任务、流式传输和背压，再使用Rust优化热点。

9. **简单易用来自产品抽象**  
   用户选择服务套餐，平台处理CNI、CSI、GPU和Karmada细节。

10. **可靠性优先于功能数量**  
    新插件必须同时具备监控、升级、备份、安全、诊断和回滚能力，才可标记为生产可用。
